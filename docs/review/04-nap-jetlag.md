# 04 Nap and Jet lag

Scope: `EveryTime/Features/Sleep/Nap/`, `EveryTime/Features/Sleep/JetLag/` (all files read in full). Paths below are relative to `EveryTime/Features/Sleep/` unless they start with `EveryTime/`.

## P0
- None found.

## P1
- `Nap/NapAlarm.swift:218-227`: the iOS 26 system alarm has no `stopIntent`/`secondaryIntent`, and nothing watches `AlarmManager.alarmUpdates`. Stopping the alarm ("I'm up" on 26.0, "Stop" on 26.1+) never calls `NapSession.finish`. Example: alarm rings at 15:00, the user stops it and opens the app at 17:00. The nap is still "in progress", and "I'm up" logs 2 h 20 m instead of 20 min. A 3 h+ gap turns it into a night (`Nap.isNight`). The pre-26 chain's "I'm up" action does log the nap, so the two paths behave differently. → Pass a `LiveActivityIntent` as `stopIntent` that runs `NapSession.finish(at: alarm time)`. Or, on activation, finish any active nap whose system alarm id is no longer in `AlarmManager.shared.alarms`, using `nap.alarm` as the end.

## P2
- `Nap/NapAlarm.swift:33-36,87,138-146`: `NapAlarm.schedule` runs in unserialized `Task`s. `cancel()` runs first, and the alarm id is saved only after `await SystemAlarm.schedule`. Example: two quick taps on "Up at" chips (`moveAlarm`) start two Tasks. Each cancels before either has saved its id, so the first alarm is never cancelled and `systemKey` is overwritten. The orphaned alarm rings at the old time. The same applies if Cancel lands during the await: the alarm is saved after the cancel and rings for a dropped nap. On the pre-26 path, `scheduleChain` can add its 8 notifications after a cancel the same way. → Serialize like `JetLagNotifications.queue` (chain the previous Task). After each await, check that `NapKey.active` still equals `nap`; if not, cancel the alarm or chain you just created.
- `JetLag/JetLagNotifications.swift:6,54`: jet lag always adds 40 and ignores free slots. The other features do respect free slots (events 20, countdown 10, lunar 10), so the total budget is 80, over iOS's 64 cap. The nap chain (9), WindDown (1) and ActivityLog marks add more. All four reschedules run at the same time on `.active` (`EveryTimeApp.swift:31-34`), each working from its own snapshot of the pending list. With a trip planned, iOS silently drops the farthest-out requests, and the next run gives events only `64 - 40 - …` slots. The doc comment ("leaves room for important events") doesn't hold. → Use `min(limit, free)` like the siblings. Better: one shared budget helper that splits the 64 slots by priority and runs every feature's reschedule in a single serialized pass (step 12).
- `JetLag/JetLagNotifications.swift:6` + `EveryTime/EveryTimeApp.swift:31`: only the next 40 actions are queued, and the queue is refilled only when the app becomes active. That is about 5–7 actions per day (sleep, bright, some light, avoid light, no caffeine, melatonin). A 9 h eastbound plan with 2 pre-adjust days runs about 10 days. If the app isn't opened during the trip, reminders stop partway through. → Skip informational kinds (`someLight`) like `caffeineOK`, and add a `BGAppRefreshTask` that calls `reschedule()`.
- `SleepTimeView.swift:63`: the profile sheet on the Sleep page writes `JetLagKey.profile` (bed/wake, chronotype, age) but never calls `JetLagNotifications.reschedule`. Only `JetLagTripsView` reacts (`JetLag/JetLagTripsView.swift:33`). Pending reminders keep the old times until the app is next backgrounded and reopened. → Reschedule wherever the profile is saved (e.g. in a `JetLagProfile` save helper), not in a single view's `onChange`.
- `JetLag/JetLagPlanner.swift:18,27`: offsets are sampled once, at `trip.departure` for the origin and `stage.arrival` for the destination. (a) DST change inside the pre-adjust window: say NYC, departure Mar 15 2027, 2 pre-adjust days. `firstCBT` sits at 04:00 EST (UTC-5), but `alignedTo` is EDT (-4). The whole plan is 1 h off, and the "adapted" wake lands at 08:00 instead of 07:00. (b) A destination DST change while still adjusting gives the same 1 h error. → Use `origin.secondsFromGMT(for: firstCBT)` for `alignedTo`. For targets, re-read `secondsFromGMT(for: cbt)` each cycle inside `BodyClock.cycles` (treat a DST jump as a 1 h step change in the target), not a fixed `Target.offset`.

## P3
- `Nap/NapAlarm.swift:283,342`: if the app was suspended (e.g. another app took the audio session without sending `.ended`), the `asyncAfter` ring fires as soon as the app resumes. Opening the app hours after the alarm time starts a 10-minute ring. → In `ring()`, skip it when `Date.now > nap.alarm + a few minutes`.
- `Nap/NapAlarm.swift:144`: on iOS < 26, `NapSession.plan(bed:wake:)` arms the muted keep-alive loop from the moment you plan. A plan made at 20:00 for a 07:00 wake keeps background audio running for 11 h. → Accept it, but say so in `NapAlarmStatus`, or recommend AlarmKit / plugging in for planned nights.
- `Nap/NapAlarm.swift:352`: `willPresent` returns `[]` for every non-nap category. Jet lag, countdown, event and wind-down reminders never show while the app is open. That matches iOS's default, but this delegate is the one place to change it. → Return `[.banner, .list]` for the other prefixes (e.g. `jetlag.`).
- `Nap/NapAdvice.swift:133`: `tonight()` with no `bed` falls back to `day(of: start).bed`. History rows (`SleepTimeView.swift:376`, `nap.bed` is usually nil) use that fallback, while `SleepNow` uses `current(at:)`. Example: bed 01:00, wake 08:00, a nap at 00:15. The planner rates it high (bed in 45 min); the history row shows green (bed in about 24 h). → Default to `current(at: start).bed` when that is after `start`, else `day(of:)`.
- `Nap/NapRows.swift:142-160`: `LogNapSheet` caps the start at now but not the end. Start 5 min ago plus 20 min logs a nap that ends in the future, marked natural, and it feeds `SleepCycle.relearn`. → Clamp `minutes` so `start + minutes <= now`, or disable Save.
- `Nap/NapAlarm.swift:40,66`: `kind(_ minutes:)` ignores its argument, and `max(end, nap.start)` is redundant after the `end > nap.start` guard. → Drop both.
- `JetLag/JetLagPlanner.swift:10` + `JetLag/TripPlanning.swift:10-13`: `plan(now:)` is never read, so `Trip.plan`'s `min(now, start)` anchoring does nothing. → Remove the parameter or use it.
- `JetLag/JetLagPlanner.swift:85-104`: light windows are cut by sleep but not by awake flight time. The plan, and the notification "See bright light — get outside or near a window", can land mid-flight. → Subtract `flights` too, or use plane-friendly copy for pieces inside a flight.
- `JetLag/JetLagNotifications.swift:57,65`: body times use `day.timeZone`. On the landing day that is the destination zone even before landing, while the phone still shows origin time ("Sleep if you can · Until 06:30"). → Add the city name when `timeZone != .current`, e.g. "06:30 Tokyo".
- `JetLag/JetLagTripsView.swift:15,38`: `TimelineView(.everyMinute)` rebuilds every trip's full plan each minute just to get its status text. → Cache plans keyed by `(trip, profile)`, or only recompute status.
- `JetLag/NewTripSheet.swift:61,116,266`: `draft.plan(for:)` runs up to 3 times per render (`problem` via `canCreate`, `summary`, and `problem` again inside `summary`). → Compute it once per body.

## Improvements
- Verified OK: trip delete reschedules notifications via `onChange(of: trips)`, and stale requests are removed by prefix. There is no trip-edit UI (only delete and the bell toggle). Backup restore and leaving demo mode both reschedule. Date-line and half-hour zones work, because offsets are GMT seconds and `wrapped` picks the shorter of advance or delay.
- Add unit tests for `JetLagPlanner`: eastbound, westbound, a ±12 h tie, the Kiribati/Hawaii 24 h case (expect no plan), DST inside the pre-adjust window, and a stopover under/over 48 h.
- Factor the near-identical `reschedule`/`isAuthorized`/queue code shared by JetLag, Events, Countdown and Lunar into one notification scheduler that owns the 64-slot budget.
